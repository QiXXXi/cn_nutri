# cn_nutri —— 中文版 nutrimatic

[nutrimatic.org](https://nutrimatic.org) 让你用近似正则的模式反查英文词条。中文缺一个
对应物：中文的检索维度是**每个字的语音与字形属性**——韵母、声调、笔画、结构、部首。

给定「一个四字词语，第一个字的韵母是 ai/an/ang 之一，第二个字是第三或第四声，
第三个字不多于 7 画，第四个字是独体字或左右结构」，本工具能查出全部符合的答案：

```
$ cn-nutri "[a,an,ang][~3,~4][7-][独体,左右]" --limit 4 --no-color
命中 1590 条（显示第 1–4 条）
  弹道导弹  dàn dào dǎo dàn   4字 频872 左右/半包围/上下/左右  ballistic missile
  大大小小  dà dà xiǎo xiǎo    4字 频479 独体/独体/独体/独体    large and small; of all sizes
  浪漫主义  làng màn zhǔ yì   4字 频397 左右/左右/独体/独体    romanticism
  马列主义  mǎ liè zhǔ yì     4字 频360 独体/左右/独体/独体    Marxism-Leninism
```

> 计划里写的验收数字是「命中 240 条」，**没有复现**。数据抓齐后实测 1590 条，
> 而计划自己点名的 胆战心惊 / 安史之乱 / 三五成群 / 弹道导弹 一个不少。那个数多半
> 来自当时还没抓完的结构数据（结构判不了的字会被排除，数出来偏小）。

## 安装与构建

纯标准库，零第三方依赖（Python ≥ 3.10）。

```bash
pip install -e .                    # 提供 cn-nutri 命令
python -I tools/build_db.py         # data_raw/ -> data/cn_nutri.db（约 8 秒）
python -I tools/build_client_data.py  # 网页用的客户端词库（约 10 秒）
python -m pytest tests/             # 454 个测试（其中 53 个要 node，见「客户端引擎」）
```

`data/cn_nutri.db` 是构建产物（约 59 MB），已随仓库提供。想从原始数据重头构建，
见下面「数据来源」。

## 用法

### 命令行

```bash
cn-nutri "[a,an,ang][~3,~4][7-][独体,左右]"        # 整词锚定，逐字约束
cn-nutri "*[氵]*" --limit 20                        # 含某个部件的任意词
cn-nutri "*[⿰弓长]*"                                # 含拆字为「⿰弓长」的字的词
cn-nutri "[a][~1][a][~1]" --sort len                # 换排序：freq/len/strokes/pinyin
cn-nutri "[a,an][~3]" --idiom                       # 只要成语
cn-nutri "[氵][氵]" --stats                         # 显示耗时与扫描量
cn-nutri                                            # 无参数进交互模式
```

### 网页

```bash
python -m cn_nutri.server            # 默认 127.0.0.1:8000，端口被占自动顺延
python -m cn_nutri.server --open     # 顺手打开浏览器
```

页面分三块：

- **DSL 输入框**：实时语法校验。无法识别的条件会**逐条列出来**而不是静默丢弃，
  语法错误定位到字符偏移并给 caret 提示。
- **逐字约束表单**：每位一行（字面・韵母・声母・声调・笔画・结构・部首・六书），
  与 DSL 文本框**双向同步**。
- **难输入部件面板**：点选即插入光标处。分「常用偏旁 / 康熙部首 214 / 按笔画 1–13+」
  共 15 组，笔画组按笔画数排序。生僻部件多在 CJK 扩展区（`𠀁` U+20001…）乃至扩展 G
  （`𰀁` U+30001…）——179 个里 171 个不在基本区，**系统字体普遍没有字形**，所以随项目
  内置了一份 35 KB 的子集字体，把它们当真文字渲染：能选中、能跟随字号缩放、与旁边的
  字基线对齐。见 [src/cn_nutri/web/fonts/](src/cn_nutri/web/fonts/)。

命令行与网页共用 `search()` 这一条查询路径，两端行为不会漂移。

### 客户端引擎

网页版**默认不连后端**：解析 DSL、扫描 36.8 万词、排序，全在浏览器里跑，服务器只发
三个静态文件（`web/engine.js`、`web/data/tables.json`、`web/data/corpus.bin`）。
把整个目录当静态站点丢上去就能用，`python -m cn_nutri.server` 只是本地预览的一种方式。

动机在服务器侧：每个请求都要占着 GIL 扫一遍全量词表，实测 24 并发时中位延迟从
135 ms 涨到 2.5 s。挪到客户端后服务器不再参与查询，这个瓶颈就不存在了。

**顺带快了十倍。**同一批查询，Python 参考实现与本机 node 跑移植版（中位数）：

| 查询 | 命中 | Python | 客户端 JS |
|---|---|---|---|
| `[a,an,ang][~3,~4][7-][独体,左右]` | 1,590 | ~100 ms | **5.4 ms** |
| `[左右][左右][左右][左右]` | 3,094 | ~120 ms | **5.0 ms** |
| `[7-][7-][7-][7-]` | 7,670 | ~130 ms | **7.5 ms** |
| `?[~1]` | 26,712 | ~165 ms | **17.7 ms** |
| `*[氵]*` | 43,249 | ~1.4 s | **122 ms** |
| `*[左右][7-]*` | 118,077 | — | **128 ms** |

V8 对紧循环和 TypedArray 的优化把定长查询压进了 10 ms 以内——这反而**达到了**计划里
那个「P95 < 100 ms」的目标（Python 一侧没达到）。复现：

```bash
node tools/bench_client.js          # 词库 12.87 MB 解码一次 8 ms，不计入上表
```

**词库格式**（`python -I tools/build_client_data.py`，产物 12.87 MB / gzip 5.56 MB；
加 `--no-definitions` 是 8.07 MB / gzip 3.30 MB，代价是结果页没有释义）：

- 字符表、部件表、音节表**按使用次数降序**排，于是词记录里的下标绝大多数小于 256、
  高字节恒为 0，gzip 能把这一半直接压掉。
- 不存 `pinyin_display`（4.1 MB）、`sort_aux`（2.9 MB）和词的文本（1.1 MB）——三者
  都是可现算的。`--check` 会读回来逐字段核对，不是「应该能推出来」。
- 每段补齐到 4 字节边界：段长不总是 4 的倍数（`chars.strokes` 就是 7,533 字节），
  而 JS 的 `Uint32Array` 视图起点没对齐就直接抛 `RangeError`。

**正确性**由 [tests/test_client_engine.py](tests/test_client_engine.py) 盯着：同一批
查询分别喂给 JS 引擎与 Python 参考实现，**逐字段比对整份响应**——spans、命中读音下标、
读音来源、拼音串、释义，以及 `excluded_missing` / `missing_chars` / `scanned` 这些
统计量。少比一个字段，那个字段就会静静地漂。跑它要 node；没装 node 时整模块 skip，
**skip 不是通过**。

`web/data/` 里的三个文件是构建产物，随仓库提供；只有从原始数据重建才需要 `data_raw/`。

## 查询语言

**一个 `[...]` 描述一个字的全部条件；组内同类条件取并集，不同类条件取交集。**

| 类别 | 写法 | 语义 |
|---|---|---|
| 韵母 | `a` `an` `ang` `v`(=ü) … | 并集 |
| 声母 | `b` `m` `zh` …，`xx` = 零声母 | 并集 |
| 声调 | `~1` `~2` `~3` `~4`，`~5`/`~0` = 轻声 | 并集 |
| 笔画 | `8` = 恰 8 画，`8-` = ≤8，`16+` = ≥16 | 并集 |
| 结构 | `独体` `左右` `上下` `左中右` `上中下` `半包围` `全包围` | 并集 |
| 六书 | `象形` `指事` `会意` `形声` | 并集 |
| 部首/部件 | `氵` `日` `扌` …（裸写单字） | 并集 |
| 拆字 | `⿰弓长` `⿱艹化`（IDS 串，以算子开头） | 并集 |
| 字面 | `(沐露二勾恶感)` | 并集 |

为什么不需要用不同括号区分类别：声母表与韵母表**交集为空**，声调带 `~`、笔画是纯
数字、结构是词、字面集带括号——各类的书写形态天然不重叠。

**字位与通配：**

```
[a,an,ang][~3,~4][7-][独体,左右]    四字词，逐字约束
?                                   任意一个字
*                                   任意序列（0 个或多个），用于「包含」类查询
张[a,an]                            第 1 字「张」，第 2 字韵母 a/an
*[左右][7-]*                         含「左右结构且 ≤7 画」该字的任意词
```

**符号不区分全半角**（`，～－＋（）【】［］` 与半角等价），**空格一律忽略**，
**无法识别的条件被忽略并另行列出**。整词锚定，`\` 转义。

**多音字按语境判定**：约束匹配的是该词**在该语境下**的真实读音，而不是字的孤立读音。
`银行` 是 yínháng、`行走` 是 xíngzǒu，同一个「行」在两个词里韵母不同——所以
`银[ang]` 命中「银行」，`[ing][~3]` 命中「行走」。一个词有多套读音时，任一套满足即
命中，结果页会高亮命中的那一套。

### 完整示例

```
[氵，m ,a, e，~3,b,左右，8-,(沐露二勾恶感),10，i,  xx ， 上下，xx, ~4，u，v,16+,o，这是啥, idontknow】
```

解析为**同一个字**的约束：韵母 ∈ {a,e,i,u,v,o}、声调 ∈ {3,4}、笔画 ∈ {≤8, =10, ≥16}、
结构 ∈ {上下, 左右}、部首 = 氵、声母 ∈ {m, b, 零声母}、字面 ∈ {沐,露,二,勾,恶,感}；
`这是啥` 与 `idontknow` 因无法识别被忽略。

## 一个必须先讲的坑：结构不能从 IDS 推

IDS（表意文字描述序列，如 `⿰弓长`）**无法表达「独体字」**。两个独立数据源实测：

| 字 | 应为 | 字统网 | makemeahanzi | 汉典「字形结构」 |
|---|---|---|---|---|
| 白 | 独体 | `⿱丿日` → 上下 ✗ | `⿻？日` → 镶嵌 ✗ | **单一结构** ✓ |
| 日 | 独体 | `⿴囗一` → 全包围 ✗ | `⿴口一` → 全包围 ✗ | **单一结构** ✓ |
| 大 | 独体 | `⿻人一` → 镶嵌 ✗ | `⿻一人` → 镶嵌 ✗ | **单一结构** ✓ |
| 山 | 独体 | `⿶凵丨` → 下三包围 ✗ | `⿶凵丨` → 下三包围 ✗ | **单一结构** ✓ |
| 张 | 左右 | `⿰弓长` ✓ | `⿰弓长` ✓ | 左右结构 ✓ |

（「字统网」列是定方案时探测的值；本地缓存只抓了 348 个字就停了，其余用
makemeahanzi 兜底，所以你现在查 `白` 看到的 IDS 是 makemeahanzi 的 `⿻？日`。）

IDS 是**到笔画/最小部件级别的图形拆分**，描述「怎么画」，不是「是不是独体字」。这
不是权威性高低的问题——字统网的数据里根本没有结构分类这个字段。

所以：**结构以汉典「字形结构」为准**（汉典写「单一结构」，查询侧归一成 `[独体]`），
IDS 只用来做拆字检索。

| 属性 | 来源 | 位置 |
|---|---|---|
| 词 + 词级拼音 + 释义 | CC-CEDICT | `data_raw/cedict/cedict_ts.u8` |
| 词频 | jieba `dict.txt` | `data_raw/jieba/jieba-master/jieba/dict.txt` |
| 单字读音 | pinyin-data | `data_raw/pinyin_data/pinyin-data-master/pinyin.txt` |

| IDS 拆字 / 难输入部件表 | 字统网 zi.tools（抓取） | `data_raw/zitools/` |

因为字统网压根没有这个字段（见上一节）。

### 重新抓取

```bash
python -I tools/fetch_zdic.py --chars data_raw/corpus_chars.txt \
                              --out data_raw/zdic --delay 0.25
python -I tools/fetch_zitools.py --workers 6      # 可选，慢
python -I tools/build_db.py
```

内置字体（生成物已随仓库提供，改动部件表或想换字体时才需要重跑）：

```bash
python -I tools/build_parts_font.py       # 需要 fontTools，只在构建时装
```

汉典抓取带磁盘缓存、可随时中断续抓，只需约 1 小时。字统网的 IDS 接口对常用字要
5–20 秒一个字，全量 7,533 字要跑几小时；**默认不抓**，用 makemeahanzi 兜底
（覆盖 6,777/7,533），字统网缓存有的字优先。`fetch_zitools.py` 支持断点续抓，
想补就跑。

## 排序

词频（jieba）覆盖不全，所以主排序是三级：

- **Tier 0** `freq > 0` → 按 jieba 词频降序
- **Tier 1** `freq == 0` 但在 CC-CEDICT → 按字频和降序
- **Tier 2** jieba 独有 → 按字频和降序

Tier 1 排在 Tier 2 之前，是因为 CEDICT 收录的是经过人工甄别的真词，不该被 jieba 里
那些切分歧义产生的低频串埋掉。「字频和」＝该词各字的语料总频次之和，让零频词也有
一个可解释的次序。另提供 `--sort len|strokes|pinyin`。

## 性能

**计划里写的「P95 < 100 ms」没有达到，这里如实记录实测值。**

计划在做方案时测到「全量 37.8 万词暴力扫描 12 ms/次」，据此决定不建索引。这个数字
在实现后**没能复现**——真实的全量扫描是秒级，不是毫秒级。本轮做了一轮优化（把
每个字都要重算的 `stroke_set()` 提到查询前算一次、定长模式免去回溯、只要前 k 条时用
堆选而不全排序），本机实测：

| 查询 | 命中 | 中位耗时 |
|---|---|---|
| `[a,an,ang][~3,~4][7-][独体,左右]` | 1,590 | ~100 ms |
| `[左右][左右][左右][左右]` | 3,094 | ~120 ms |
| `[7-][7-][7-][7-]` | 7,670 | ~130 ms |
| `?[~1]` | 26,712 | ~165 ms |
| `*[氵]*` | 43,249 | ~1.4 s |

定长查询（逐字约束，输入即回报的常见形态）在 100–200 ms 量级；含 `*` 的查询要扫全量
36.8 万词，慢一个数量级。真要压到 100 ms 以内，得给部件/笔画这类字形条件建一张
**每查询现算的字符集缓存**（7,533 个字，一张表几毫秒就能算出，之后每个字位的判定
退化成一次集合查找），或者持久化的倒排索引——这一版没做。

**但网页版已经不需要这些了**：同一套逻辑移植到 JS 后由 V8 跑，上表里最快的几条掉到
5–8 ms、最慢的 128 ms，见下面「客户端引擎」。上表保留着，是因为它仍是**命令行**
（纯 Python）的真实代价，同时也是移植前后对照的基线。

端到端测试里的性能用例卡的是**中位耗时 300 ms**，用意是「防止再退化」，而不是守住
那个达不到的目标。之所以不用 P95：十几个样本的 P95 就是第二差的那次，机器一忙就飘
（同一份代码实测过 100 ms 也实测过 640 ms），中位数才扛得住负载抖动。

## 已知限制

- 汉典覆盖词库里的 7,533 个字，其中 **9 个字没有结构/六书数据**（都是扩展区的生僻字，
  汉典本站也没有）；抓不到的回退 makemeahanzi 的 IDS，再回退标 `unknown`。
  另有 24 个字汉典会固定返回 504——不是限流，是那几页在汉典自己的缓存里坏掉了，
  `fetch_zdic.py` 重试时带上一次性查询串绕开缓存即可，已经抓全。
- **字形数据缺失的字不会「静默放行」**：某个字的属性判不了，含这个字的词就判为不命中，
  并计入 `excluded_missing` 在结果页提示「N 个词因数据缺失无法判定而被排除」。把
  「不知道」当成「满足」才是静默答错。
- 结构标签以汉典口径为准（汉典写「单一结构」，查询侧做别名归一，写 `[独体]` 即可）。
- 部件面板的字形来自随项目内置的子集字体。**一个字体不够**：179 个部件里只有 8 个在
  基本区，思源黑体只覆盖 19 个（扩展 B 一个都没有），要靠遍黑体补——两者合起来才
  179/179，所以是三个字体文件按 `unicode-range` 分流。删掉 `web/fonts/` 目录，
  页面照样能跑，只是生僻部件会退回系统字体、可能显示成豆腐块。
- **词库里没有单字词**：最短 2 字。CC-CEDICT 与 jieba 收的都是词，单字不成条目。
  所以 `[日]`、`[⿰弓长]` 这类**只有一个 `[]`** 的查询恒为空——它描述的是一字词。
  想按部首/拆字找字得写成包含式：`*[日]*`、`*[⿰弓长]*`。计划 §九.6 写的
  「`[氵]` 应命中 沐/江/海」按字面根本不可能成立，那几条用例从设计上就是错的。
- 笔画只支持「恰 N / N- / N+」，不支持区间（避免与已取消的 `3-4` 式声调语法混淆）。
- 部首按「该字的部首 ∈ 给定集合」匹配；裸写单字同时按拆字匹配（语义是并集），所以
  `[日]` 既命中「明」（部首日）也命中「白」（拆作 `⿻？日`，部件里含「日」）。
- jieba 独有的词没有 CEDICT 拼音，用**词内位置条件化的读音先验**推定，多音字可能推错；
  这些读音标 `inferred`，命令行显示 `?` 角标。
- 儿化、古音、姓氏特殊读音（如「单」shàn）覆盖不完整。
- 声调按**词汇本调**存储，不做变调（「一」「不」的变调不反映）。
- 排序是词频近似，不是语料库精确频次。
